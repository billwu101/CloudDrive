**兩部的分工必須講清楚，否則會互相以為對方測過了**——這正是 §33 整章漏接的成因：後端整合測試全過，前端單元測試全過，但沒有任何一層檢查「這兩端接在一起」。

| | 第一部 API | 第二部 Playwright |
|---|---|---|
| 驗證對象 | 後端契約、資料落地、權限隔離 | 前端接線、使用者流程、渲染正確性 |
| 資料來源 | 真 Postgres + 真 storage | 真後端（不得用 MSW mock） |
| 抓得到 | 丙 | 甲、乙、丙 |
| 抓不到 | 甲、乙（完全看不到前端） | 邊界值與錯誤碼（成本太高，不該在這層做） |
| 對應指令 | `uv run pytest tests/integration` | `npm run test:e2e` |

**分層原則**：能在 API 層驗的就不要拉到 Playwright（慢 50 倍且不穩）。Playwright 只驗**非得開瀏覽器才驗得到**的事——渲染、互動、接線、跨頁狀態。

## 1. API 測試的驗證層級

寫入端點回 `200` **不代表資料寫對了**。`db5b2b7`（星號查詢範圍錯）當時寫入端點回 200、單元測試也過，但換一支端點查就查不到。因此規定：

| 級 | 驗證到什麼 | 抓得到什麼 |
|---|---|---|
| **A1 回應** | 狀態碼正確、body 形狀符合契約 | 端點不存在、欄位名錯、錯誤碼錯 |
| **A2 落地** | **另外呼叫一次查詢端點**確認狀態真的改變 | 收了但沒做、寫錯地方、查詢範圍錯 |
| **A3 副作用** | 連帶狀態正確：配額、`file_versions`、`activity_logs`、storage blob | 補償回滾沒做、孤兒 blob、版本沒建 |
| **A4 隔離** | 換一個使用者 / 不帶 token / 猜 UUID，一律拒絕 | 權限只比對 owner、越權存取 |

**強制規則**

1. 寫入類端點**最低 A2**。禁止只斷言寫入端點自己的回應。
2. 涉及配額、版本、稽核、blob 的**最低 A3**。
3. 所有受保護端點**都要有 A4**，對應 §24 驗收標準第 1、2 點。
4. A2 的查詢必須是**獨立的一次請求**，不可重用寫入回應的 body。

## 6. Playwright 的驗證層級

`31c8b67`（PDF 預覽）當時斷言的是 `<iframe>` 存在——元素確實在，但預覽根本出不來。因此規定：

| 級 | 驗證到什麼 | 抓得到什麼 |
|---|---|---|
| **E1 請求** | 實際發出了預期的 request（method + path） | 甲類：前端根本沒打後端 |
| **E2 反映** | 畫面正確反映結果——**含內容或狀態，不只是存在** | 渲染錯誤、顯示了但值是錯的 |
| **E3 持久** | **`page.reload()` 後**仍然正確 | 只改了前端 state、後端沒存 |
| **E4 跨主體** | 換帳號／無痕視窗確認，效果對別人也成立 | 權限問題、分享沒真的生效 |

**強制規則**

1. 使用者可見功能**最低 E3**。權限與分享類**最低 E4**。
2. **禁止 `toBeVisible()` 作為唯一斷言。** 要確認元素就一併確認其內容或狀態（值、數字、disabled、aria-checked）。
3. E3 的 reload 必須是真的 `page.reload()`，不可只等前端 refetch——TanStack Query 的快取會讓沒存進後端的東西看起來還在。

## 7. 全域守門（每個測試自動套用）

這三個守門比任何個別 case 都有效，因為它們讓**靜默失敗變成不可能**。

```ts
// e2e/fixtures.ts
export const test = base.extend({
  page: async ({ page }, use) => {
    const errors: string[] = []
    page.on('console', m => { if (m.type() === 'error') errors.push(`console: ${m.text()}`) })
    page.on('pageerror', e => errors.push(`pageerror: ${e.message}`))
    page.on('response', r => {
      if (r.url().includes('/api/') && r.status() >= 400)
        errors.push(`HTTP ${r.status()} ${r.request().method()} ${r.url()}`)
    })
    await use(page)
    expect(errors, `偵測到未預期的錯誤：\n${errors.join('\n')}`).toEqual([])
  },
})
```

| 守門 | 抓什麼 | 若當時就有，會攔下哪個事故 |
|---|---|---|
| **G-1 console 無 error** | 未捕捉的例外、渲染錯誤 | — |
| **G-2 無未預期 4xx/5xx** | 前端打錯路徑、沒帶 token、後端炸掉 | `7a35bb0`（404）、`4e7ac32`（401）、`c2952db`（500） |
| **G-3 二進位資源走 blob** | 全站不得有 `<img>`／`<iframe>` 的 src 直指受保護 API | `4e7ac32` |

測錯誤路徑的 case 需自行 allowlist 預期的狀態碼。

## 13. 維護規則

1. **新增功能必須先在本表補 case**，標明 ID 與級別，才可動工（CLAUDE.md「文件先行」）。
2. **每修一個 bug，必須補一條 case 並標註 commit hash**。已標註的 hash 都是真實回歸點，不得刪除。
3. 新增 case 時先問：**這件事能不能在第一部驗完？** 能就不要放進第二部——Playwright 慢 50 倍且不穩。
4. 判定準則若以 `toBeVisible()` 為唯一斷言，**視為未完成**。
5. 實測結果回填到 `doc/tasks/<module>.md`。
6. proposal 新增章節時，其「驗收標準」節的每一條都要在本表找得到對應 case。
